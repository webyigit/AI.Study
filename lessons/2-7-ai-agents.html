Module 2-7

AI 에이전트란 무엇인가

"챗봇은 대답하고, 에이전트는 일한다" — 이 한 문장의 차이가 실제로 무엇을 의미하는지, 그리고 그 차이가 만드는 위험까지 함께 살펴봅니다.

본문 한눈에 정리 용어 상세 참고문헌

Phase 2를 통해 우리는 LLM이 다음 토큰을 예측하는 원리부터, 컨텍스트의 한계, 환각, 그리고 RAG로 외부 지식을 끌어오는 방법까지 살펴봤습니다. 이번 모듈은 Phase 2의 마지막 조각입니다. 지금까지 다룬 LLM이 "혼자서 여러 단계를 계획하고 실행하는 존재"로 확장되면 무슨 일이 벌어지는지 — 바로 AI 에이전트입니다.

1) 챗봇과 에이전트, 뭐가 다른가

지금까지 우리가 대화해온 일반적인 챗봇은 한 가지 패턴을 따릅니다. 사용자가 메시지를 보내면, 모델이 한 번 생각해서 텍스트 답변 하나를 돌려주고 끝입니다. 다음 단계가 필요하면 사람이 다시 메시지를 보내야 합니다. 즉, 매 턴마다 사람이 운전대를 잡고 있는 구조입니다.

AI 에이전트는 이 구조를 바꿉니다. 에이전트는 세 가지를 스스로 할 수 있습니다.

① Tool use(도구 사용) — 텍스트로 답하는 것을 넘어 실제 API·함수를 호출해 진짜 데이터를 가져오거나 실제 행동을 취할 수 있습니다.
② 자율적 다단계 실행 — 사람이 매 단계를 일일이 지시하지 않아도, 지금까지의 결과를 보고 "다음에 뭘 해야 하는지" 스스로 판단해 여러 단계를 이어서 수행합니다.
③ 플래닝(계획 수립) — 하나의 메시지에 단순 반응하는 게 아니라, 목표를 이루기 위한 계획을 먼저 세우고 그 계획에 따라 움직입니다.

비유하자면, 챗봇은 "질문을 받으면 아는 선에서 답해주는 인턴"에 가깝고, 에이전트는 "목표만 던져주면 알아서 조사하고 처리한 뒤 결과를 보고하는 직원"에 가깝습니다.

2) Tool use — 에이전트가 "손발"을 갖는다는 것

LLM 자체는 학습 시점에 저장된 지식과 눈앞의 프롬프트만으로 텍스트를 생성하는 존재입니다. 실시간 정보를 조회하거나, 실제로 이메일을 보내거나, 사내 시스템에 접근할 방법이 원래는 없습니다. Tool use는 이 한계를 메우는 장치입니다.

개발자(혹은 기획자가 설계에 관여하는 시스템)는 모델에게 미리 "이런 도구를 쓸 수 있다"는 목록을 알려줍니다. 예를 들면 "웹 검색", "계산기", "이메일 보내기", "사내 DB 조회" 같은 도구들이고, 각 도구마다 무엇을 하는지, 어떤 입력이 필요한지 설명이 붙어 있습니다. 모델은 사용자의 요청을 보고 이 요청을 처리하려면 어떤 도구를, 어떤 입력값으로 호출해야 할지를 스스로 판단합니다. 도구가 실행되고 결과가 돌아오면, 모델은 그 결과를 다음 판단의 재료로 사용합니다. Module 2-5에서 다룬 RAG의 "검색"도 사실 에이전트 관점에서 보면 하나의 도구 호출로 이해할 수 있습니다.

3) 자율실행과 플래닝 — 생각·행동·관찰을 반복

에이전트가 여러 단계를 이어가는 과정은 흔히 "생각(Think) → 행동(Act) → 관찰(Observe) → 다시 생각"이라는 루프로 설명됩니다. 목표를 받으면 먼저 어떻게 접근할지 계획을 세우고(생각), 필요한 도구를 호출하고(행동), 그 결과를 확인한 뒤(관찰), 그 결과를 바탕으로 계획을 다시 다듬거나 다음 행동을 정합니다. 목표를 달성했다고 판단되거나, 정해둔 조건(예: 최대 단계 수)에 도달하면 이 루프를 멈추고 최종 결과를 사람에게 보고합니다.

예시 — "이번 주 경쟁사 앱 업데이트 내역을 조사해서 정리해줘"
일반 챗봇이라면 자신이 학습 당시 알고 있던(그리고 이미 오래됐을 수 있는) 정보로만 답하거나, "실시간 정보에는 접근할 수 없다"고 답할 것입니다.
반면 에이전트는 이렇게 움직일 수 있습니다: (1) "경쟁사 앱 업데이트"를 웹 검색 도구로 조회 → (2) 검색된 여러 페이지 중 관련성 높은 몇 개를 읽기 도구로 열람 → (3) 정보가 부족하다고 판단되면 다른 키워드로 재검색 → (4) 모은 정보를 종합해 정리된 답변을 작성. 이 전 과정에서 사람은 처음 목표만 주고, 중간 단계마다 다시 지시할 필요가 없습니다.

4) 한계와 위험 — 왜 에이전트는 더 조심스럽게 설계해야 하는가

자율성이 커진 만큼, 에이전트는 챗봇에는 없던 위험도 함께 가지고 옵니다. 기획 단계에서 반드시 고려해야 할 대표적인 문제 세 가지입니다.

① 루프(무한 반복) — 에이전트가 같은 도구를 비슷한 방식으로 계속 반복 호출하면서 실질적인 진전은 없는 상태에 빠질 수 있습니다. 예를 들어 검색 결과가 마음에 들지 않으면 살짝 다른 검색어로 계속 재검색만 반복하는 식입니다. 이런 상황을 막으려면 "최대 몇 단계까지만 시도하고 멈춘다"처럼 명확한 중단 조건을 미리 정해둬야 합니다.

② 잘못된 도구 호출 — 모델이 상황을 오판해서 엉뚱한 도구를 선택하거나, 도구에 잘못된 입력값을 넘기는 경우입니다. 특히 단계가 여러 개로 이어지는 작업에서는, 초반 한 단계의 실수가 이후 모든 단계에 그대로 전파되어 결과 전체가 틀어질 수 있습니다.

③ 되돌릴 수 없는 실제 행동의 위험 — 챗봇이 틀린 답을 주는 것과, 에이전트가 틀린 판단으로 실제 이메일을 보내거나 실제 결제를 진행하거나 실제 데이터를 수정하는 것은 무게가 다릅니다. 후자는 실제 세계에 되돌리기 어려운 영향을 남깁니다. 그래서 실무에서 에이전트를 설계할 때는 (a) 위험도가 높은 행동(발송·결제·삭제 등) 앞에는 사람의 확인 단계를 넣고, (b) 실행할 수 있는 최대 단계 수나 시간에 제한을 걸고, (c) 각 단계의 판단 과정을 로그로 남겨 사후에 검토할 수 있게 하는 가드레일이 함께 따라와야 합니다.

정리하면

구분챗봇AI 에이전트
동작 방식메시지 하나에 답변 하나(반응형)목표를 받아 여러 단계를 스스로 실행
도구 사용기본적으로 없음(텍스트 응답만)API·검색·DB 조회 등 외부 도구 호출
진행 방식매 턴 사람이 다시 지시생각→행동→관찰을 스스로 반복
대표 위험잘못된 텍스트 답변(환각 등)무한루프, 잘못된 도구 호출, 되돌릴 수 없는 실제 행동

에이전트는 "더 똑똑한 챗봇"이 아니라, 텍스트 응답을 넘어 실제 행동을 취할 수 있는 완전히 다른 종류의 시스템입니다. 그만큼 얻는 것도 크지만, 설계 단계에서부터 안전장치를 함께 고민해야 하는 이유이기도 합니다.

이해 확인 — 여러분이라면 "사내 정책 챗봇"을 "사내 업무 자동화 에이전트"로 확장할 때, 어떤 행동에는 반드시 사람의 확인을 거치게 만들지 한두 가지 떠올려보세요. 이것으로 Phase 2(LLM 제대로 이해하기)를 마칩니다. 다음 Phase에서는 이 개념들을 실제로 활용하는 방법을 다룹니다.

Tool use (도구 사용)

↑ 본문으로

LLM이 텍스트 생성만으로는 할 수 없는 일 — 실시간 정보 조회, 외부 API 호출, 실제 시스템 조작 등 — 을 미리 정의된 "도구"를 호출해서 수행하는 방식입니다. 모델은 사용자의 요청을 보고 어떤 도구를, 어떤 입력값으로 호출할지 스스로 판단하며, 도구 실행 결과를 다시 자신의 다음 판단 재료로 사용합니다. 에이전트를 일반 챗봇과 구분 짓는 가장 결정적인 특징입니다.

자율실행 (Autonomous Execution)

↑ 본문으로

사람이 매 단계를 일일이 지시하지 않아도, 에이전트가 "생각(계획) → 행동(도구 호출) → 관찰(결과 확인) → 다시 생각"의 과정을 스스로 반복하며 목표를 향해 나아가는 것을 말합니다. 목표 달성 또는 정해진 중단 조건(최대 단계 수 등)에 도달하면 루프를 멈춥니다. 자율성이 커지는 만큼 무한루프나 잘못된 판단이 누적될 위험도 함께 커지므로, 명확한 중단 조건과 확인 단계 설계가 중요합니다.

RAG (검색증강생성)

↑ 본문으로

Module 2-5에서 다룬 개념으로, 모델이 답변하기 전에 관련 지식을 외부 저장소에서 검색해 프롬프트에 삽입하는 방식입니다. 에이전트 관점에서 보면 RAG의 "검색" 단계도 하나의 도구 호출로 볼 수 있어, RAG는 에이전트가 활용하는 여러 도구 중 하나로 자연스럽게 통합됩니다.
