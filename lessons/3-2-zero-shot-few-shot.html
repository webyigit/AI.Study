Module 3-2

Zero-shot vs Few-shot

어떤 날은 그냥 바로 물어보는 것만으로 충분하고, 어떤 날은 예시 두세 개를 먼저 보여주는 것만으로 결과물의 품질이 확 달라집니다. 이 모듈에서는 두 방식이 정확히 무엇이고 언제 어떤 것을 써야 하는지를 다룹니다.

본문 한눈에 정리 용어 상세 참고문헌

3-1에서 프롬프트를 Role · Context · Instruction · Format 네 요소로 나눠 짜는 법을 배웠습니다. 이번 모듈의 few-shot 예시들은 그 구조 어딘가에 새로 끼워 넣는 다섯 번째 조각이 아니라, Instruction 안에(혹은 별도의 Examples 덩어리로) 들어가서 "이렇게 하라"는 말을 "이런 식으로 하라"는 구체적인 견본으로 바꿔주는 역할을 합니다. Zero-shot과 few-shot의 차이는 결국 "그 견본을 넣을 것이냐 말 것이냐"의 차이입니다.

1) Zero-shot — 예시 없이 바로 지시하기

Zero-shot은 모델에게 예시를 하나도 보여주지 않고, 지시문(Instruction)만으로 바로 작업을 시키는 방식입니다. "다음 문장을 요약해줘", "이 문장의 감정을 분류해줘"처럼, 우리가 평소 챗봇에 던지는 질문 대부분이 사실 zero-shot입니다.

예시 — "다음 이메일 제목을 한 줄로 요약해줘: '안녕하세요, 지난주 문의드린 환불 건이 아직 처리되지 않아 다시 연락드립니다...'" 이렇게 묻는 순간이 전형적인 zero-shot입니다. 어떤 형식으로, 몇 글자로 요약할지에 대한 견본은 주지 않았습니다.

zero-shot의 장점은 단순합니다. 프롬프트가 짧고, 작성하는 데 시간이 거의 들지 않습니다. 모델이 사전에 학습한 지식만으로도 충분히 대답할 수 있는, 흔하고 정의가 명확한 작업이라면 이걸로 충분합니다.

2) Few-shot — 예시를 몇 개 보여주고 시작하기

Few-shot은 본격적인 작업 요청 전에, 프롬프트 안에 "입력 → 원하는 출력" 짝을 2~3개 직접 적어 넣는 방식입니다. 이렇게 프롬프트 문장 속에 실제 견본을 예시제공하면, 모델은 그 견본들에 공통으로 깔린 규칙을 순간적으로 알아채고 다음 입력에도 같은 규칙을 적용합니다. 이를 모델이 패턴학습을 한다고 표현합니다.

여기서 중요한 포인트는, 예시가 모델에게 알려주는 게 "무엇을 할지(주제)"가 아니라 "어떻게 할지(형식·기준·톤)"라는 점입니다. "감정을 분류해줘"라는 지시만으로도 모델은 이미 감정 분류가 뭔지 압니다. 모델이 모르는 건 "당신이 정확히 어떤 카테고리 이름을 쓰고 싶은지, 애매한 경우는 어느 쪽으로 몰지, 답을 몇 줄로 얼마나 자세히 쓰고 싶은지" 같은 세부 규칙입니다. 예시 2~3개는 이 세부 규칙을 말이 아니라 실물로 보여주는 가장 확실한 방법입니다.

예시 — "고객 피드백을 칭찬/불만/제안/혼합 중 하나로 분류해줘"라는 지시만 주면 모델은 네 카테고리의 경계를 자기 나름대로 추측합니다. 하지만 "혼합"으로 분류된 견본 하나를 미리 보여주면, 모델은 "아, 칭찬과 불만이 섞여 있으면 혼합으로 묶는구나"라는 기준을 그대로 따라 합니다.

3) 언제 무엇을 써야 할까

Zero-shot으로 충분한 경우 — 작업이 단순하고, 흔하며(모델이 학습 과정에서 비슷한 케이스를 많이 봤을 것 같고), "정답"의 형태가 딱히 애매하지 않은 경우입니다. 예를 들어 "이 문장을 존댓말로 바꿔줘", "이 숫자를 반올림해줘" 같은 작업은 예시 없이도 결과가 충분히 안정적입니다.

Few-shot이 값어치를 하는 경우 — 다음 네 가지 신호 중 하나라도 해당되면 예시를 넣는 편이 낫습니다.

① 출력 형식이 애매할 때 — "표로 정리해줘"보다 실제 표 한 줄을 보여주는 게 빠릅니다.
② 특정 톤·스타일이 필요할 때 — 브랜드 보이스, 존댓말 수위처럼 말로 설명하기 번거로운 것.
③ 엣지케이스 처리가 중요할 때 — "칭찬과 불만이 동시에 있으면 어떻게 하지?" 같은 경계 사례.
④ 구조화된 출력을 매번 똑같은 형식으로 뽑아야 할 때 — API에 넣을 JSON, 표 형식의 라벨링 등.

대신 few-shot은 프롬프트 길이를 늘리고, 그만큼 토큰 비용도 커집니다. 그러니 "예시 없이 몇 번 시켜봤는데 결과가 들쭉날쭉하다"는 확인이 된 다음에 few-shot으로 넘어가는 것이 효율적인 순서입니다.

4) 실전 예제 — 고객 피드백 톤 분류하기

같은 작업을 zero-shot과 few-shot으로 각각 시켜보면 차이가 눈에 보입니다. 과제는 "고객 피드백을 칭찬 / 불만 / 제안 / 혼합 중 하나로 분류하라"입니다.

(a) Zero-shot 프롬프트
"다음 고객 피드백의 톤을 분류해줘: '배송이 너무 늦어서 화가 나요. 그래도 포장은 예쁘게 잘 왔어요.'"

그럴듯하지만 어정쩡한 출력
"이 피드백은 전반적으로 부정적입니다." — 카테고리 이름이 프롬프트에서 정한 네 가지("칭찬/불만/제안/혼합")와 다르고, 칭찬과 불만이 함께 있다는 사실이 "부정적"이라는 한 단어로 뭉개졌습니다. 게다가 같은 질문을 다시 던지면 이번엔 "혼합적인 의견입니다"처럼 답의 형식 자체가 매번 바뀔 수 있습니다.
(b) Few-shot 프롬프트
"다음 고객 피드백을 칭찬 / 불만 / 제안 / 혼합 중 하나로 분류하고, 이유를 한 줄로 설명해줘.

예시 1
입력: "상담원분이 정말 친절했어요, 최고예요!"
출력: 칭찬 — 상담원 응대에 대한 긍정적 평가만 담겨 있음

예시 2
입력: "앱이 자꾸 튕겨요. 빨리 고쳐주세요."
출력: 불만 — 문제 제기와 개선 요청이지만 전체적으로 부정적 경험이 중심

예시 3
입력: "배송은 느렸지만 포장은 예뻤어요. 다음엔 배송만 더 빨랐으면 좋겠어요."
출력: 혼합 — 부정적 경험(배송)과 긍정적 경험(포장)이 함께 있고 제안까지 포함됨

이제 다음 피드백을 같은 형식으로 분류해줘:
입력: "배송이 너무 늦어서 화가 나요. 그래도 포장은 예쁘게 잘 왔어요."
출력:"

개선된 출력
"혼합 — 배송 지연에 대한 불만과 포장에 대한 칭찬이 함께 있음" — 카테고리 이름, 출력 형식("카테고리 — 이유")이 예시와 정확히 일치하고, 칭찬과 불만이 섞인 엣지케이스도 "혼합"으로 올바르게 처리됐습니다.
(c) 무엇이 달라졌나 — zero-shot 결과는 매번 다른 단어와 형식으로 답이 나올 수 있고, 혼합된 감정을 한쪽으로 뭉개는 경향이 있었습니다. few-shot에서는 ① 카테고리 이름이 항상 프롬프트에서 정한 네 개 중 하나로 고정되고, ② "카테고리 — 이유" 형식이 매번 그대로 유지되며, ③ 예시 3에서 미리 보여준 "혼합" 패턴 덕분에 비슷한 엣지케이스도 정확히 분류됩니다. 지시문의 내용은 거의 그대로인데, 예시 세 줄이 추가됐을 뿐입니다.

정리하면

구분Zero-shotFew-shot
프롬프트 길이짧다 — 지시문 한두 문장길다 — 지시문 + 예시 2~5개
적합한 상황단순하고 흔하며 정의가 명확한 작업형식이 애매하거나, 특정 톤·스타일이 필요하거나, 엣지케이스 처리가 중요하거나, 구조화된 출력을 일관되게 뽑아야 할 때
장점빠르게 작성 가능, 토큰 비용이 적음출력 형식·품질이 훨씬 일관되고 정확함
단점애매한 케이스에서 결과가 들쭉날쭉할 수 있음프롬프트가 길어져 토큰 비용 증가, 예시 품질이 나쁘면 오히려 역효과

결론적으로 few-shot이 항상 더 좋은 건 아닙니다. 작업이 단순하면 zero-shot으로 끝내고, "결과가 매번 다르게 나온다" 싶을 때 예시제공으로 넘어가는 것이 순서입니다.

이해 확인 — 최근에 썼던 zero-shot 프롬프트 하나를 골라, 예시 2개를 추가한 few-shot 버전으로 직접 바꿔보세요. 다음 모듈(3-3. Chain-of-Thought)에서는 모델이 답만 툭 내놓는 게 아니라, 그 답에 이르는 추론 과정을 단계적으로 "보여주게" 만드는 방법을 다룹니다.

예시제공 (Example-Providing)

↑ 본문으로

예시제공은 프롬프트 안에 "입력과 그에 대한 바람직한 출력" 짝을 실제 문장으로 적어 넣어주는 것을 말합니다. 지시문만 주는 것과 달리, 모델이 그대로 참고할 수 있는 구체적인 견본을 직접 보여준다는 점이 핵심입니다. 예를 들어 "피드백을 톤별로 분류하라"는 지시만 주는 대신, "입력: 배송이 너무 늦어요 → 출력: 불만" 같은 예시 2~3개를 프롬프트 문장 안에 함께 적어 넣는 것이 예시제공입니다. 예시제공을 하면 모델이 무엇을, 어떤 형식으로 답해야 하는지 훨씬 명확해져서 결과의 형식과 일관성이 크게 좋아집니다. 3-1에서 배운 프롬프트 구조 중 Instruction 부분이나 별도의 Examples 덩어리에 이 견본들을 넣어주면 됩니다.

패턴학습 (Pattern Learning, in-context learning)

↑ 본문으로

패턴학습은 모델이 프롬프트에 주어진 몇 개의 예시만 보고, 그 예시들에 공통으로 깔린 입력-출력 규칙을 그 자리에서 파악해 다음 입력에 그대로 적용하는 현상을 말합니다. 모델을 다시 훈련시키는 것이 아니라 이번 대화 안에서만 일어나는 일시적인 적응이라, 흔히 "인컨텍스트 러닝(in-context learning)"이라고도 부릅니다. 예를 들어 "칭찬/불만/제안/혼합" 네 카테고리로 라벨링된 예시 3개를 보여주면, 모델은 "이 네 카테고리 중 하나로, 이 정도 형식으로 답하면 되는구나"라는 패턴을 스스로 학습해 다음 피드백에도 같은 규칙을 적용합니다. 패턴학습이 잘 일어나려면 예시들이 서로 다른 케이스(전형적인 칭찬, 전형적인 불만, 애매한 혼합 등)를 골고루 보여주는 것이 중요합니다. 예시가 서로 너무 비슷하면 모델이 그만큼 좁은 패턴만 배우게 됩니다.
