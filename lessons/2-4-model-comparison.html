Module 2-4

GPT vs Claude vs Gemini vs 오픈소스 모델 비교

"어떤 모델이 제일 좋아요?"라는 질문 대신, 작업의 성격에 따라 모델 범주를 고르는 durable한 기준을 세웁니다.

본문 한눈에 정리 용어 상세 참고문헌

이 모듈은 "지금 이 순간 어느 모델이 제일 똑똑한가"를 알려주는 랭킹이 아닙니다. 랭킹은 몇 달만 지나도 바뀝니다. 대신 모델비교를 어떤 축으로 해야 오래 쓸 수 있는지, 그 기준 자체를 익힙니다.

1) 왜 "최고의 모델"이라는 질문이 틀렸는가

기획자나 실무자가 AI 도구를 고를 때 가장 자주 하는 실수는 "GPT-5가 Claude보다 벤치마크 점수가 높으니 GPT-5를 쓰자"처럼 특정 시점의 순위표로 결정하는 것입니다. 문제는 이 업계가 몇 주 단위로 새 모델이 나오는 속도전이라는 데 있습니다. 오늘의 1등이 다음 분기엔 3등이 되기도 하고, 벤치마크 점수 자체도 측정 방식에 따라 크게 흔들립니다.

그래서 이 모듈에서는 "지금 몇 점이다"가 아니라 어떤 작업에는 어떤 범주의 모델이 구조적으로 유리한가를 다룹니다. 모델 이름과 순위는 바뀌어도, "긴 문서를 신중하게 다루는 성향", "검색·멀티모달 통합이 강한 성향", "직접 운영해서 데이터를 안 내보내는 선택지" 같은 범주의 성격은 상대적으로 오래갑니다.

2) 독점(proprietary) 모델 3사의 일반적 성향 — GPT · Claude · Gemini

OpenAI의 GPT 시리즈, Anthropic의 Claude 시리즈, Google의 Gemini 시리즈는 모두 최상위권 성능을 놓고 경쟁하는 범용 LLM입니다. 세 회사 모두 계속 업데이트를 내놓기 때문에 "이번 달 기준 1등"은 자주 바뀌지만, 각 회사가 제품을 만들어온 방향성과 생태계 위치는 비교적 꾸준히 유지되는 경향이 있습니다. 아래는 정확한 벤치마크 순위가 아니라 일반적으로 관찰되는 성격입니다.

GPT 시리즈(OpenAI)는 가장 폭넓은 생태계를 가지고 있다는 평가를 받습니다. 플러그인, 각종 서드파티 통합, 음성모드, 이미지 생성까지 한 제품 안에 다 갖춘 "만능 도구"에 가깝게 발전해 왔고, 개발자 생태계(API, 확장 도구)도 가장 넓게 퍼져 있습니다.

Claude 시리즈(Anthropic)는 처음부터 안전성 연구를 중심에 두고 만들어진 회사의 모델답게, 긴 글을 신중하게 읽고 쓰는 능력과 차분하고 절제된 답변 태도로 자주 언급됩니다. 긴 문서·코드베이스를 붙여넣고 꼼꼼히 분석하게 하거나, 톤을 다듬어야 하는 글쓰기 작업에 강하다는 평가가 꾸준합니다.

Gemini 시리즈(Google)는 이미지·동영상·텍스트를 함께 다루는 멀티모달 능력과, 구글 검색·Gmail·문서 도구·유튜브 등 구글 생태계와의 통합이 특징입니다. 최신 정보 검색이 필요하거나 구글 인프라(예: Google Cloud, Firebase) 위에서 개발 중이라면 자연스럽게 붙는 선택지입니다.

예시 — 사내 신제품 소개 자료의 문체를 다듬고 싶다면 Claude, 유튜브 트렌드나 최신 뉴스를 실시간으로 찾아 요약하고 싶다면 Gemini, 이미지 생성부터 음성 대화까지 여러 기능을 한 창에서 쓰고 싶다면 GPT가 자연스럽게 손이 가는 선택입니다. 이건 "더 똑똑해서"가 아니라 "그 작업에 맞게 설계돼 와서"에 가깝습니다.

3) 오픈소스 모델이라는 세 번째 선택지

GPT·Claude·Gemini는 모두 API 호출로만 쓸 수 있는 독점 모델입니다. 모델의 가중치(파라미터 값) 자체는 공개되지 않고, 회사의 서버에서만 돌아갑니다. 반면 Meta의 Llama, Mistral, Alibaba의 Qwen, DeepSeek 계열 같은 오픈소스(오픈웨이트) 모델은 모델 가중치 파일 자체를 내려받아 직접 실행할 수 있습니다.

이게 실무적으로 뜻하는 바는 세 가지입니다. 첫째, 자체 서버(온프레미스)나 우리 회사의 클라우드 계정 안에서 직접 구동할 수 있습니다. 둘째, 우리 회사 데이터로 파인튜닝(추가 학습)해서 특정 업무에 특화시킬 수 있습니다. 셋째, 특정 회사의 API에 의존하지 않기 때문에 그 회사가 가격을 올리거나 서비스를 중단해도 우리 서비스가 함께 멈추지 않습니다.

대신 트레이드오프도 명확합니다. 모델을 직접 서빙하려면 GPU 서버, 배포 파이프라인, 모니터링, 보안 패치 같은 운영 역량이 필요하고, 톱티어 독점 모델만큼의 절대 품질을 항상 따라잡는다는 보장은 없습니다. 특히 소규모 팀이라면 "공짜로 받은 모델"이 오히려 사람 손이 더 많이 드는 선택이 될 수 있습니다.

예시 — 고객센터 상담 로그처럼 외부로 절대 보내면 안 되는 데이터를 요약해야 하는 팀이 있다면, API 호출마다 데이터를 외부 서버로 보내는 독점 모델 대신 Llama나 Qwen 계열 오픈소스 모델을 사내 서버에 설치해 그 안에서만 처리하는 방식을 검토할 수 있습니다. 대신 그 서버를 누가 유지보수할지를 함께 결정해야 합니다.

4) 비용 구조 — 종량제 API vs 자체 운영비

독점 모델은 보통 토큰 단위 종량제입니다. 쓴 만큼만 내고, 초기 투자가 거의 없어서 소규모 실험이나 사용량이 적을 때는 압도적으로 저렴하고 편합니다. 다만 사용량이 폭증하면(대량 자동화, 고빈도 호출) 매달 청구서가 빠르게 커집니다.

오픈소스 모델은 반대로 고정비 구조에 가깝습니다. GPU 서버(직접 구매 또는 클라우드 임대) 비용, 이를 관리할 엔지니어 인건비가 먼저 들어갑니다. 대신 한번 인프라를 갖추면, 호출량이 아무리 늘어도 추가 과금 없이 처리할 수 있습니다. 그래서 "사용량이 적을 땐 API가 싸고, 사용량이 아주 많아지는 지점을 넘어서면 자체 운영이 더 싸진다"는 손익분기점이 존재합니다. 정확한 분기점은 모델 크기·트래픽·클라우드 단가에 따라 다르므로, 우리 팀의 예상 호출량으로 직접 계산해보는 것이 중요합니다.

5) 데이터 프라이버시 — 외부로 보낼 것인가, 안에 둘 것인가

독점 모델 API를 호출한다는 건, 우리가 입력한 텍스트(계약서 초안, 고객 데이터, 미공개 기획안 등)가 그 회사의 서버로 전송되어 처리된다는 뜻입니다. 대부분의 기업용 API는 그 데이터를 모델 재학습에 쓰지 않는다는 약관을 제공하지만, 그래도 데이터가 물리적으로 회사 바깥의 제3자 인프라를 거친다는 사실 자체는 바뀌지 않습니다. 규제 산업(금융, 의료, 법률)이나 미공개 정보를 다루는 조직에서는 이 지점이 계약·법무 검토 대상이 됩니다.

반면 오픈소스 모델을 사내 서버에서 직접 돌리면, 데이터가 회사 경계를 벗어나지 않습니다. 오프라인 환경에서도 구동이 가능하다는 것도 특징입니다. 그래서 "품질은 조금 양보하더라도 데이터가 절대 밖으로 나가면 안 되는 업무"에서는 오픈소스 자체 호스팅이 진지한 선택지가 됩니다. 이 판단은 순전히 성능 문제가 아니라, 보안·컴플라이언스 팀과 함께 정할 문제입니다.

6) 실무 선택 체크리스트 — 작업별로 무엇을 먼저 볼 것인가

결국 "어떤 모델을 쓸까"는 하나의 정답이 아니라, 아래 다섯 가지 요인을 그 작업에 맞게 저울질하는 문제입니다.

① 데이터 민감도 — 외부로 나가면 안 되는 데이터인가? 그렇다면 자체 호스팅형 오픈소스가 먼저 검토 대상입니다.
② 품질 요구 수준 — 최종 산출물이 사람이 그대로 쓸 정도로 정교해야 하는가, 아니면 초안 수준이면 충분한가? 정교함이 최우선이면 최상위권 독점 모델이 여전히 유리한 경우가 많습니다.
③ 비용·호출량 — 하루 몇 번 쓰는 실험인가, 하루 수십만 건 처리하는 자동화인가? 후자로 갈수록 자체 운영의 경제성이 커집니다.
④ 속도(지연시간) — 실시간 응답이 필요한 제품인가, 배치로 나중에 처리해도 되는 작업인가?
⑤ 생태계 연동 — 이미 구글 워크스페이스나 특정 클라우드에 깊이 물려 있다면, 그 생태계에 맞는 모델이 통합 비용을 크게 줄여줍니다.

예시 — 네 가지 상황
· 아이디어 브레인스토밍(가벼움, 데이터 민감도 낮음) → 아무 독점 모델이나 빠르게. 속도와 편의가 우선.
· 사내 계약서·인사 문서 분석(데이터 민감도 최상) → 오픈소스 자체 호스팅 또는 기업용 프라이빗 API 검토.
· 고객 문의 자동 분류 같은 대량·저비용 자동화(호출량 매우 많음) → 사용량이 임계점을 넘으면 자체 운영 오픈소스가 유리.
· 이미지가 섞인 자료 요약 같은 멀티모달 작업 → 멀티모달을 잘 지원하는 독점 모델 계열이 아직 유리한 경우가 많음.

중요한 건 이 다섯 가지 축을 스스로 점검하는 습관이지, 이 문서가 알려주는 "지금 이 모델이 최고다"라는 문장이 아닙니다. 그런 문장은 이 글을 쓰는 시점에도 이미 낡아가고 있습니다.

정리하면

기준독점 모델(GPT·Claude·Gemini 등)오픈소스 모델(Llama·Mistral·Qwen·DeepSeek 등)

모델 이름과 순위는 이 페이지를 다시 읽는 시점엔 달라져 있을 가능성이 높습니다. 하지만 "데이터는 어디로 가는가", "비용은 사용량에 따라 어떻게 변하는가", "품질을 어디까지 요구하는가"라는 세 가지 질문은 앞으로도 계속 쓸 수 있는 모델비교의 뼈대입니다.

이해 확인 — 지금 맡고 있는 업무 하나를 골라, 위 다섯 가지 체크리스트(데이터 민감도·품질·비용·속도·생태계)로 어떤 모델 범주가 맞을지 스스로 판단해보세요. 다음 모듈(2-5. RAG, 검색 증강 생성이란 무엇인가)에서는 "모델 자체를 바꾸지 않고도 최신 정보나 사내 문서를 답변에 반영하는 방법"을 다룹니다.

모델비교 (Model Comparison Framework)

↑ 본문으로

여러 LLM 중 어떤 것을 쓸지 판단하는 체계적인 방법을 뜻합니다. 특정 시점의 벤치마크 순위 하나로 결정하는 방식은 모델 업데이트 주기가 몇 주 단위로 짧아진 지금은 오래가지 않습니다. 대신 데이터 민감도, 비용 구조, 품질 요구 수준, 응답 속도, 생태계 연동처럼 시간이 지나도 유효한 "판단 축"을 기준으로 비교하는 것이 모델비교 프레임워크의 핵심입니다.

벤치마크 (Benchmark)

↑ 본문으로

여러 모델의 성능을 같은 문제 세트로 채점해 비교하는 표준화된 시험입니다. 수학 문제, 코딩 문제, 상식 퀴즈 등을 모아 정답률을 %로 매기는 식입니다. 다만 실무에서 벤치마크 점수를 그대로 믿는 것은 위험합니다. ① 새 모델이 나올 때마다 순위가 몇 주 만에 뒤바뀌어 숫자가 금방 낡고, ② 채점 방식이나 문제 구성에 따라 같은 모델도 다른 점수가 나올 수 있으며, ③ 벤치마크 문제 자체가 모델 학습 데이터에 이미 섞여 들어가 점수가 실제 실력보다 부풀려지는 경우도 보고됩니다. 그래서 이 커리큘럼에서는 정확한 점수 대신, 시간이 지나도 잘 안 바뀌는 "성향·용도 적합성" 중심으로 모델을 설명합니다.

오픈소스 모델 / 오픈웨이트 (Open-source, Open-weight)

↑ 본문으로

모델의 학습된 가중치(파라미터 값) 파일 자체를 누구나 내려받아 자신의 서버에서 실행할 수 있게 공개한 모델입니다. Llama, Mistral, Qwen, DeepSeek 계열이 대표적입니다. API 호출 없이 직접 구동하므로 데이터를 외부로 보내지 않고, 원하는 대로 추가 학습(파인튜닝)해 업무에 맞게 커스터마이즈할 수 있습니다. 다만 서버·GPU 확보, 배포, 보안 유지 같은 운영 부담은 사용하는 조직이 직접 져야 합니다.

파인튜닝 (Fine-tuning)

↑ 본문으로

이미 대규모로 사전 학습된 모델을, 우리 회사의 데이터나 특정 업무 패턴으로 추가 학습시켜 그 분야에 더 잘 맞게 다듬는 과정입니다. 오픈소스 모델은 가중치 자체를 손에 쥐고 있기 때문에 파인튜닝이 비교적 자유롭지만, 대부분의 독점 모델은 회사가 제공하는 제한된 형태의 커스터마이징만 허용합니다.
