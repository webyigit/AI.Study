Module 5-2

AI 기능 기획서: 정상케이스와 실패케이스 정의

일반 기능 기획서는 "잘 됐을 때"만 그리면 되지만, AI 기능 기획서는 AI가 틀렸을 때·확신이 없을 때 무엇을 할지까지 정해줘야 비로소 완성됩니다.

본문 한눈에 정리 용어 상세 참고문헌

"로그인 버튼을 누르면 홈 화면으로 이동한다"처럼, 일반 기능은 성공했을 때의 흐름 하나만 정의해도 대부분 충분합니다. 그런데 AI 기능은 다릅니다. AI는 매번 확신을 갖고 정답을 내놓는 게 아니라, 어떨 때는 맞고 어떨 때는 애매하고 어떨 때는 확신에 차서 틀립니다. 기획서에 "AI가 추천한다"라고만 써 두면, 그 세 가지 상황 중 어느 것도 정의하지 않은 것과 같습니다.

1) 일반 기획서와 AI 기획서의 차이

일반 기능 기획서는 대체로 해피 패스(happy path), 즉 모든 게 예상대로 흘러갔을 때의 동작 하나만 정의합니다. 버튼을 누르면 API를 호출하고, 성공하면 화면을 바꾼다 — 이 정도로도 개발자가 무엇을 만들어야 할지 알 수 있습니다. 실패는 "네트워크 오류 시 토스트 메시지 표시" 정도로 짧게 덧붙이면 그만입니다. 실패할 확률이 낮고, 실패의 원인도 명확하기 때문입니다.

AI 기능은 이 전제가 무너집니다. AI의 출력은 100% 확신을 갖고 하는 판단이 아니라 확률적인 추정이기 때문에, "정상적으로 작동했다"와 "실패했다" 사이에 아주 넓은 회색지대가 존재합니다. 심지어 AI는 스스로 틀렸다는 사실을 인지하지 못한 채, 마치 정답인 것처럼 자신 있게 잘못된 답을 내놓기도 합니다. 그래서 AI 기능 기획서는 반드시 세 가지 시나리오를 각각 따로 정의해야 완성됩니다.

2) 세 가지 케이스: 정상 · 불확실 · 실패

정상 케이스(happy path)는 AI가 확신을 가지고 있고, 그 판단이 실제로 맞는 경우입니다. 이때는 AI가 별다른 개입 없이 결과를 그대로 실행하거나 보여줘도 됩니다. 일반 기능 기획서와 가장 비슷한 부분입니다.

불확실 케이스(low-confidence case)는 AI가 판단은 내렸지만 확신이 충분하지 않은 경우입니다. 여기서 기획자가 정해야 할 것은 "확신이 낮으면 AI가 어떻게 행동할지"입니다. 사용자에게 먼저 물어볼지, 확신도를 화면에 함께 보여줄지, 아니면 아예 AI 판단을 쓰지 않고 더 단순한 비-AI 기본 동작(규칙 기반 기본값 등)으로 되돌아갈지를 결정해야 합니다. 이 경계선, 즉 "confidence가 몇 % 미만이면 불확실 케이스로 취급한다"는 기준 자체도 기획서에 숫자로 적혀 있어야 개발팀이 구현할 수 있습니다.

실패/오류 케이스(wrong case)는 AI가 확신을 가지고 있었는데 실제로는 틀린 경우입니다. 가장 위험하면서도 가장 자주 빠뜨리는 케이스입니다. 여기서 기획서가 답해야 할 질문은 세 가지입니다. 사용자가 AI가 틀렸다는 사실을 어떻게 알아차리는가, 사용자가 그것을 얼마나 쉽게 되돌리거나 고칠 수 있는가, 그리고 그 수정 기록이 다시 시스템 개선에 반영되는가입니다.

이 세 케이스 외에도, 입력값 자체가 비정상이거나(예: 센서 값이 아예 들어오지 않음), 서로 다른 신호가 충돌하는(예: 사용자는 "덥다"고 했는데 센서는 "적정 온도"라고 함) 상황까지 폭넓게 고려하는 것이 더 넓은 의미의 예외처리입니다. 정상·불확실·실패 세 케이스가 "AI 판단 결과"에 대한 분기라면, 예외처리는 그 이전 단계인 "AI가 판단할 재료 자체가 부실한 상황"까지 포함하는 더 큰 우산입니다.

3) 왜 이걸 엔지니어가 아니라 기획자가 정의해야 하는가

"AI가 틀렸을 때 어떻게 할지는 개발하면서 알아서 처리하겠지"라고 생각하기 쉽지만, 실제로는 그렇게 되지 않는 경우가 많습니다. 기획서에 실패 케이스가 명시되어 있지 않으면, 개발자는 어쩔 수 없이 그 자리에서 즉흥적으로 동작을 정하게 됩니다. 어떤 개발자는 조용히 무시하고, 어떤 개발자는 에러 로그만 남기고 사용자에게는 아무 표시도 하지 않을 수 있습니다. 팀마다, 심지어 같은 팀 안에서도 기능마다 실패 처리 방식이 제각각이 되는 이유입니다.

더 나쁜 시나리오는, 실패 케이스가 아예 논의조차 되지 않은 채 제품이 출시되는 경우입니다. 이 경우 AI가 조용히 틀린 판단을 실행해버리고, 사용자는 그것을 되돌릴 방법도, 신고할 방법도 없는 상태에 놓입니다. 이런 경험을 한두 번만 겪어도 사용자는 그 AI 기능 전체를 신뢰하지 않게 되고, 신뢰를 잃은 AI 기능은 아무리 성능이 좋아도 다시 쓰이지 않습니다.

홈닉처럼 AI 판단이 실제 물리적 장치를 제어하는 스마트홈 서비스에서는 이 위험이 훨씬 커집니다. 쇼핑 추천 AI가 틀리면 "마음에 안 드는 상품 하나"가 뜨는 정도로 끝나지만, 온도 조절이나 조명, 도어락을 제어하는 AI가 확신을 갖고 틀리면 한밤중에 난방이 꺼지거나, 외출 중에 조명이 계속 켜져 있거나, 최악의 경우 잠겨야 할 문이 열리는 일이 벌어질 수 있습니다. 그래서 "이 기능이 틀렸을 때 사용자가 얼마나 쉽고 빠르게 되돌릴 수 있는가"는 기능의 편의성만큼이나, 어떤 경우에는 그보다 더 중요하게 기획서에 명시되어야 할 항목입니다.

4) 예시: 홈닉 "AI 자동 온도 조절 추천" 기획서

실제로 기획서에 어떻게 녹여내는지, 홈닉의 가상 기능인 "AI 자동 온도 조절 추천"을 하나의 시나리오로 놓고 구조화해보겠습니다. 이 기능은 사용자의 과거 사용 패턴과 실내외 온도 센서 값을 바탕으로, AI가 적정 온도를 계산해 자동으로 설정을 바꿔주는 기능입니다.

항목내용
트리거 조건실내 온도가 사용자 평소 선호 범위(±1.5도)를 5분 이상 벗어나고, 최근 7일 사용 데이터가 20건 이상 축적되어 있을 때
정상 케이스 동작AI confidence가 80% 이상이면, 예측 적정 온도로 자동 설정을 바꾸고 "AI가 실내온도를 24도로 조절했어요" 알림을 표시
불확실 케이스 동작confidence가 50~80%이면 자동으로 바꾸지 않고 "지금 22도가 어떠세요?" 같은 확인 알림만 보내, 사용자가 직접 수락/거절하게 함. confidence 50% 미만이면 AI 추천 자체를 보류하고 사용자가 마지막으로 설정한 값을 유지하는 기본 동작으로 전환
실패 케이스 동작사용자가 자동 조절 직후 30분 이내에 수동으로 온도를 다시 바꾸면 "AI 추천이 틀렸다"는 신호로 간주. 원래 값으로 되돌리는 버튼을 알림에 상시 노출하고, 수동 정정 기록은 다음 추천 모델 학습 데이터에 반영
되돌리기(rollback) 방법알림을 누르지 않아도 앱 홈 화면 상단에 "방금 AI가 바꾼 설정 되돌리기" 버튼을 60분간 고정 노출. 음성으로도 "아까대로 돌려줘" 한 마디면 즉시 이전 값으로 복구
기획자가 여기서 실제로 결정한 것 — confidence 임계값(80%, 50%)이라는 숫자, 불확실할 때 "자동 실행"이 아니라 "확인 요청"으로 낮춘다는 원칙, 그리고 사용자의 되돌리기 행동이 그냥 사라지지 않고 학습 데이터로 이어진다는 설계입니다. 이 세 가지는 전부 엔지니어의 코드 구현 이전에, 기획서 단계에서 사람이 판단하고 못 박아야 하는 제품 결정입니다.

정리하면

케이스트리거 조건기획서에 명시할 것
정상 케이스AI confidence가 충분히 높고, 판단이 실제로 맞는 상황자동으로 어디까지 실행할지, 결과를 사용자에게 어떻게 알릴지
불확실 케이스confidence가 애매한 구간(임계값 미만)에 걸리는 상황임계값 숫자, 사용자에게 물어볼지 여부, 물어보지 않을 때의 기본 동작
실패 케이스AI가 확신을 가졌지만 실제로는 틀린 상황사용자가 오류를 알아채는 방법, 되돌리는 방법, 그 기록이 학습에 반영되는지

세 케이스 모두를 정의하고 나면, 마지막으로 입력 자체가 없거나 충돌하는 등 더 넓은 범위의 예외처리 목록을 별도로 점검합니다. 이 네 가지가 모두 채워졌을 때 비로소 "AI 기능 기획서"라고 부를 수 있습니다. 정상 케이스만 있는 문서는 절반짜리 기획서입니다.

이해 확인 — 지금 떠올릴 수 있는 AI 기능 아이디어를 하나 골라, 그 기능의 불확실 케이스를 한 문장으로 적어보세요. "AI가 확신이 없을 때는 ___한다"는 형태로 쓰면 됩니다. 다음 모듈로 넘어가기 전 좋은 점검이 됩니다.

시나리오 (Scenario)

↑ 본문으로

제품 기획에서 시나리오란 "어떤 사용자가, 어떤 상황에서, 어떤 입력을 주고, 시스템이 어떻게 반응하는가"를 구체적인 이야기 형태로 정리한 것을 말합니다. AI 기능 기획에서는 정상적으로 흘러가는 시나리오 하나만으로는 부족하고, 확신이 낮은 시나리오와 AI가 틀리는 시나리오까지 각각 별도로 작성해야 합니다. 시나리오를 구체적으로 쓸수록 개발팀과 디자인팀이 "이럴 때는 이렇게 동작한다"를 똑같이 이해하게 되어, 구현 단계에서의 임의 해석을 줄일 수 있습니다. 좋은 시나리오는 막연한 설명이 아니라 실제 숫자와 조건(예: confidence 80% 이상, 5분 이상 지속)을 포함합니다.

예외처리 (Exception Handling)

↑ 본문으로

예외처리는 원래 소프트웨어 개발에서 프로그램이 예상하지 못한 상황(오류, 빈 값, 잘못된 입력 등)을 만났을 때 그것을 어떻게 처리할지 미리 정해두는 것을 뜻합니다. AI 기능 기획에서는 이 개념이 더 넓게 확장됩니다. 데이터가 아예 들어오지 않는 상황, 서로 다른 신호가 충돌하는 상황, 입력값이 학습 당시와 크게 다른 극단적인 상황까지 포함합니다. 정상·불확실·실패 세 케이스가 "AI가 판단을 내린 이후"의 분기라면, 예외처리는 그보다 앞선 "AI가 애초에 제대로 판단할 수 있는 상황인가"까지 점검하는 더 큰 개념입니다. 기획서에 예외처리 목록이 빠져 있으면, 실제 서비스에서는 예상치 못한 입력을 만났을 때 시스템이 멈추거나 엉뚱하게 동작할 위험이 커집니다.
